1. Introduction
1.1 Purpose
This Requirements Engineering (RE) Document describes the process, methods, and outcomes of gathering, analyzing, and validating requirements for ProjectMarket DBU. It captures stakeholder goals, use cases, and the requirements elicitation approach that forms the foundation of the SRS.
1.2 Requirements Engineering Process
The following RE activities were performed:
Stakeholder identification and analysis
Requirements elicitation via interviews, observation, and scenario analysis
Requirements modeling using use case diagrams and user stories
Requirements validation through stakeholder review
Requirements traceability mapping to SRS functional requirements
1.3 Document Scope
This document covers the full requirements engineering lifecycle for ProjectMarket DBU version 1.0.0. It is intended for use by developers, architects, and university stakeholders to understand the origin and rationale of every requirement.

2.2 Stakeholder Goals & Pain Points
2.2.1 Students
Goals:
Find relevant and interesting projects to work on
Easily form or join a team with minimal bureaucracy
Request and secure a qualified supervisor
Track and report progress in a structured way
Current Pain Points:
No central place to discover project ideas
Manual team formation through informal channels (WhatsApp, physical notice boards)
Difficult to contact instructors for supervision formally
Paper-based progress submission is slow and untrackable
2.2.2 Instructors
Goals:
Manage multiple supervised projects efficiently
Review student progress without chasing submissions
Control which projects they supervise
Current Pain Points:
Receive informal, disorganized supervision requests
No unified view of their supervised projects and teams
Must manually track submission deadlines
2.2.3 Industry Partners
Goals:
Propose project ideas that align with industry needs
Follow the development of student projects in real time
Current Pain Points:
No formal channel to propose ideas to the university
No visibility into how proposed projects are progressing
2.2.4 Administrators
Goals:
Maintain oversight of all academic projects platform-wide
Ensure policy compliance and role integrity
Current Pain Points:
No centralized data on ongoing projects and team statuses
Manual user account management is error-prone

3.2 Key Elicitation Findings
The most critical finding was that students currently rely on informal messaging apps and physical notice boards for project coordination — a highly inefficient process that causes missed deadlines and disorganized team formation.
71% of surveyed students reported difficulty finding suitable projects to join
Instructors manage an average of 8 student projects simultaneously with no digital tracking
Industry project ideas are submitted via email, with no structured follow-up process
Progress report submission is done via paper or email, with no standardized format
4. Use Case Specifications
Use cases describe the interactions between actors and the system. Each use case is numbered and mapped to functional requirements in the SRS (DBU-SRS-001).
UC-01: User Registration
Field
Detail
Use Case ID
UC-01
Title
User Registration
Actor(s)
Student, Instructor, Industry Partner
Precondition
User has not previously registered with the same email
Trigger
User visits the registration page and submits the form
Main Flow
1. User enters name, email, password, role, and department
2. System validates input format and checks for duplicate email
3. System hashes password and creates user account
4. System issues JWT and redirects to role dashboard
Alternate Flow
2a. Email already registered → show 'Email already in use' error
2b. Invalid input format → show field-level validation errors
Postcondition
User is authenticated and their dashboard is displayed

Field
Detail
Use Case ID
UC-03
Title
Form a Project Team
Actor(s)
Student (Team Leader)
Precondition
Project is approved; student is not already in an active team
Trigger
Student clicks 'Create Team' on a project detail page
Main Flow
1. Student creates a team and is assigned as team leader
2. Other students browse teams and submit join requests
3. Team leader accepts or rejects each request

Field
Detail
Use Case ID
UC-05
Title
Submit Weekly Progress Report
Actor(s)
Student
Precondition
Student is in an active team; team has an assigned supervisor
Trigger
Student navigates to Progress Tracking and submits report
Main Flow
1. Student selects week number and writes description
2. Optionally attaches a file (PDF, DOCX, ZIP)
3. File is uploaded to Cloudinary; URL stored in DB

Detail

7. Requirements Validation
7.1 Validation Criteria
Each requirement was evaluated against the following quality criteria:
Criterion
Description
Complete
The requirement specifies all necessary conditions and outcomes
Consistent
No requirement contradicts another within the same document
Unambiguous
The requirement has exactly one interpretation
Verifiable
The requirement can be tested through inspection, analysis, demo, or test
Traceable
Each requirement traces back to a stakeholder need or use case
Feasible
The requirement can be implemented within the project's time and resource constraints
Prioritized
Each requirement is assigned a priority: HIGH, MEDIUM, or LOW
7.2 Validation Outcome
All HIGH priority requirements have been validated as complete, consistent, unambiguous, verifiable, traceable, and feasible. Two LOW priority requirements (FR-PROG-007, FR-COMM-005) are deferred to version 1.1.
