1. Introduction
1.1 Purpose
This Software Design Document (SDD) describes the complete architectural and component-level design of ProjectMarket DBU. It translates the requirements defined in the SRS (DBU-SRS-001) into a concrete technical blueprint for implementation. This document is the authoritative reference for all design decisions made during development.
1.2 Design Goals
Separation of Concerns — strict layering of controllers, services, repositories, and models
Scalability — stateless backend, connection pooling, CDN-served assets
Security by Design — RBAC enforced at every layer, not just the route
Developer Experience — typed ORM (Prisma), environment-driven config, clear folder conventions
Maintainability — versioned API, migration-managed DB schema, inline documentation

2. System Architecture
2.1 Architectural Style
ProjectMarket DBU uses a three-tier client-server architecture with a REST API as the communication layer. Real-time features are added as a WebSocket layer running alongside the HTTP server.

3.2 State Management Design
The frontend uses a hybrid state approach:
React Query — for all server-state (API calls, caching, invalidation, loading states)
Zustand — for global client-state (auth user, sidebar collapse state, notification count)
React useState/useReducer — for local component state (form values, modal open)
Socket.IO client — maintains a singleton connection; triggers Zustand state updates
3.3 API Service Layer (Frontend)
All API calls are abstracted into service modules under src/services/:
src/services/
  authService.js       // login, register, me, logout
  projectService.js    // CRUD + status update
  teamService.js       // create, join, leave, approve
  supervisorService.js // request, respond, list
  progressService.js   // submit, list, get
  adminService.js      // users, departments, stats
  uploadService.js     // Cloudinary pre-signed upload
Each service uses an axios instance with the base URL and auth interceptor:
const api = axios.create({ baseURL: import.meta.env.VITE_API_URL });
api.interceptors.request.use(cfg => {
  cfg.headers.Authorization = `Bearer ${getToken()}`;
  return cfg;
});

4.2 Middleware Design
Middleware
Design & Behavior
authenticate
Reads Bearer token from Authorization header; verifies JWT; attaches decoded user to req.user
authorize(roles)
Factory function; accepts array of permitted roles; compares with req.user.role; throws 403 if unauthorized
validate(schema)
Factory using Zod schema; validates req.body; throws 422 with field errors if invalid
rateLimiter
express-rate-limit; 100 req / 15 min on auth routes; 500 req / 15 min on all others
uploadMiddleware
multer configured with memory storage; limits files to 10MB; passes buffer to Cloudinary
errorHandler
Global async error catcher; maps error types to HTTP codes; never leaks stack traces in production
4.3 Controller Pattern
Controllers are thin — they only handle HTTP concerns and delegate to services:
// controllers/projectController.js
const createProject = async (req, res, next) => {
  try {
    const project = await projectService.createProject(req.user.id, req.body);
    res.status(201).json({ success: true, data: project });
  } catch (err) { next(err); }
};
4.4 Service Layer Pattern
All business logic lives in services. Services call repositories, never Prisma directly:
// services/teamService.js
const joinTeam = async (teamId, studentId) => {
  const existing = await teamRepo.getMembership(studentId);
  if (existing) throw new AppError('Already in a team', 400);
  const team = await teamRepo.findById(teamId);
  if (!team) throw new AppError('Team not found', 404);
  return teamRepo.addMember(teamId, studentId);
};
4.5 Repository Pattern
Repositories contain all Prisma queries. This decouples business logic from the ORM:
// repositories/teamRepository.js
const getMembership = (studentId) =>
  prisma.teamMember.findFirst({ where: { student_id: studentId } });
const addMember = (teamId, studentId) =>
  prisma.teamMember.create({ data: { team_id: teamId, student_id: studentId } });

5.1 Prisma Schema Overview
The full Prisma schema is in prisma/schema.prisma. All enums are DB-level types. All relations use explicit foreign key fields with onDelete behaviors defined.

7. Real-Time Design (Socket.IO)
7.1 Connection Lifecycle
Client connects to WSS server with JWT in socket.handshake.auth.token
Server middleware validates JWT; on failure, connection is rejected
On success, socket is joined to room: user:{userId}
If student has an active team, socket also joins team:{teamId}
Disconnection cleans up rooms automatically via Socket.IO

8. Security Design
8.1 Authentication Flow
Client POSTs credentials to /api/v1/auth/login
Server fetches user by email; compares password with bcrypt.compare()
On match, server signs JWT: jwt.sign({ sub, role, departmentId }, JWT_SECRET, { expiresIn: '24h' })
Client stores token in memory (Zustand); never in localStorage
All subsequent requests include: Authorization: Bearer <token>
authenticate middleware: jwt.verify() → attaches user to req.user
authorize(['ADMIN']) middleware checks req.user.role
8.2 Security Controls Summary
Control
Implementation Detail
Password Hashing
bcrypt.hash(password, 12) on registration; bcrypt.compare() on login
JWT Signing
HS256 algorithm; secret from env; 24h expiry; no refresh token in v1
Rate Limiting
express-rate-limit: auth routes 100/15min, general routes 500/15min
Input Validation
Zod schemas for all POST/PATCH body; strips unknown fields; throws 422
SQL Injection
Prisma parameterizes all queries; raw SQL is never used
CORS
cors() configured with allowedOrigins=[VITE_CLIENT_URL] only
Security Headers
helmet() sets: CSP, HSTS, X-Frame-Options: DENY, X-Content-Type-Options
File Validation
multer limits: 10MB max; Cloudinary validates file type on server side
Socket Auth
Socket.IO middleware validates JWT on connection; rejects invalid tokens
Error Masking
Production errors: generic message returned; details logged server-side only

9.3 Database Migration Strategy
Schema changes are made to prisma/schema.prisma
Migration generated: npx prisma migrate dev --name <change_name>
Migration file committed to version control
In production: npx prisma migrate deploy (run in Render's pre-start hook)
Rollbacks: restore previous migration state; Neon supports DB branching for safe testing
